# 从一次客服问题读懂代码

这份导读围绕一句话展开：“客户从广州搬到佛山，原来的宽带能直接迁过去吗？”包内资料是虚构演示；阅读时把它当作产品手册的样例。

## 1. 先看三部分各自负责什么

| 文件 | 主要职责 |
| --- | --- |
| `src/support_knowledge/knowledge.py` | 加载 Markdown、分段、搜索、按行读取原文 |
| `src/support_knowledge/server.py` | 把搜索和读取登记成 MCP 工具，选择通信方式 |
| `skills/support-reply/SKILL.md` | 告诉 AI 先查什么、怎样核对、最后交付什么 |

模型由宿主客户端提供。这个仓库不实现聊天界面，也不在检索函数中调用模型。

## 2. 资料怎样变成可搜索的内容

`KnowledgeBase` 在启动时读取指定目录中的 Markdown 文件。可选的文件头提供标题、适用范围和更新时间；正文按章节组织成可搜索的片段，同时记录原文件行号。

读取并保留来源位置很重要：模型如果只拿到一段没有出处的摘要，后面很难检查它有没有漏掉“跨城市”这样的限制。

## 3. 搜索时具体发生了什么

调用示意：

```json
{"query": "宽带 跨城市 移机", "limit": 5}
```

`search_knowledge` 把参数交给 `KnowledgeBase.search()`。查询和正文使用同一种切分方式：中文取相邻双字，英文取单词。BM25 根据词项匹配、词频与片段长度排序。

因此，搜索结果里的 `score` 是排序分数。例如 `3.2` 不表示“正确率 320%”，也不是“有 3.2 分把握”。命中了“移机”的文档，仍可能只讲同城移机，需要继续读条件。

## 4. 为什么搜索后还要读原文

搜索返回 `source_id`、`start_line`、`end_line` 等字段。AI 再调用：

```json
{"source_id": "实际搜索返回的文件 ID", "start_line": 1, "max_lines": 80}
```

`read_source` 返回带行号的内容。原文太长时，`next_start_line` 表示下一页从哪里开始。`version` 是文件内容摘要，帮助区分不同资料快照。

文件 ID 来自已加载的知识库，不是任意文件读取入口。数据加载时还会检查文件范围；用户不能通过参数要求读取另一个目录里的密码文件。

## 5. MCP 在中间做了什么

客户端向服务询问可用工具，SDK 返回工具名称、用途和参数结构。模型选择工具后，宿主发送调用请求，SDK 解析参数、找到函数并返回结果。

我们写的是“搜索什么、返回什么”；通用的消息协议交给 SDK。默认 stdio 由客户端启动子进程并交换消息。HTTP 模式把同一组工具提供在本机 `/mcp` 地址。

本项目不把任何调试文字打印到 stdio 的标准输出，避免普通日志混进协议消息。

## 6. Skill 怎样改变回复过程

它要求先看城市、产品等条件，读完整条款，再分别写客户正文和内部记录。查到跨城市规则，不代表查到了客户的合同或违约金；这部分要列为待确认事项。

Skill 不能让不存在的工具自动出现，也不保证模型每次都遵守。可机械检查的参数和文件边界写在程序里；如何组织回复、是否需要追问，则交给模型结合 Skill 处理。

## 7. 读源码时可以验证的三个问题

1. 搜索一个资料里完全没有的主题，为什么应返回空列表，而不是拼出答案？
2. 把资料改掉但不重启服务，会看到哪个版本？本项目采用启动时快照，重启才加载新版本。
3. 为什么搜索结果要保留行号和版本，而不是只返回一段摘要？它们让人工能核对同一份原文。

可以在自己的资料目录添加一节新规则，重启服务，搜索并读取它。不要为了练习修改现有正式业务资料。
